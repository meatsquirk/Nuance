# bs-10 Daltonization — behaviour-test completeness

Independent adversarial grade of the bs-10 daltonization acceptance suite. I did **not** write these tests and changed no test or product file. Two behaviour phases have now landed and **un-pended** their ACs, so this is a re-grade against the previous (first) grid, not a fresh one:

- **AC-1 (DALT-3)** — `daltonize` is now the **real** error-redistribution remap (not the identity shell): it takes the painter's full-strength `projectDichromat` view, measures the a*/b* chroma lost to that collapse, rotates it 90° in the a*/b* plane, and adds it back scaled by severity, with lightness preserved. The one chokepoint `displayedSwatchColor` applies it per the painter's stored profile. `AC-1`'s test now runs in the default suite and is graded against the **independent** `referenceDaltonize`, never the shipped `daltonize` against itself.
- **AC-5 (DALT-4)** — the one chokepoint (`displayedSwatchColor`, fed `AppScope.cvdProfile`) drives the remap from the **stored** profile's type **and** severity, not a default. DALT-4 changed no `lib/` body; it un-pended AC-5 and added unit tests pinning that the chokepoint forwards the stored type and severity and that severity scales the remap.

The remaining **eight** ACs are still **pending** (stage 3), graded on their design — what the code asserts — not on whether they currently skip. Four of them (AC-2/3/4/8) are **green at the shell baseline by design**: turning daltonization on does not yet drive a screen-level behaviour their Then can separate from "off", so each carries a pre-seeded augmentation row owned by a behaviour phase and is graded **"B pending <phase>"**, not A. The other four still-pending ACs (AC-6/7/9/10) fail at the red baseline on a real Then or precondition — they discriminate today — and are graded against grade-A design.

Surfaces read to verify every Then is tight and aimed at the right surface: `integration_test/daltonization_test.dart` (the AC tests + `_remapOf` / `_expectKnownSwatchRemapped`), `integration_test/daltonization_harness.dart` (the Given/When/Then vocabulary, fixtures, the independent `referenceDaltonize`, `displayColorOf`/`colorNear`/`displaySwatches`), `integration_test/bs10/pending.dart` (the pending gate), the spec `specs/bs-10-daltonization.feature`, the catalogue + augmentations in `MASTER_PLAN_FOR_FEATURE.md` (§"Acceptance integration test plan") and `modules/ITEST.md` (§"Red baseline" / §"Test augmentations"). Product code read to grade the shipped behaviour: `lib/a11y/cvd/daltonize.dart` (`daltonize`/`daltonizeColor`), `lib/display/color_simulation.dart` (`displayedSwatchColor` chokepoint), `lib/widgets/color_chip.dart` (reads `AppScope.cvdProfile` → chokepoint), `lib/display/display_read_endpoint.dart`, `lib/display/settings_screen.dart` (no-profile region still an empty placeholder — CONTROL-2 not landed).

**Grading discipline.** The remap (AC-1/AC-5/AC-6/AC-9) is graded against `referenceDaltonize` — an **independent** in-harness error-redistribution remap built on bs-08's independent `referenceProjectDichromat`, never the shipped `daltonize` against itself — via `colorNear` (summed-channel tolerance 0.05 ≈ 13/255, ≈ 4 per channel; tightened from the scaffold's 0.094 by DALT-3 so the smallest real remap — protan ≈ 0.078 — still registers as changed). AC-7's "distinct from simulation" contrast likewise uses the independent `referenceProjectDichromat`. The verified red-baseline run (`--dart-define=BS10_RUN_PENDING=true`) now: runs the un-pended **AC-1/AC-5** and passes them against the shipped real remap (agreeing with `referenceDaltonize` to the 8-bit swatch); passes AC-2/3/4/8 (green-at-baseline/limited); and fails AC-6/7/9/10 on their tight Then or named precondition (the live re-read DALT-11, the distinction DALT-5, the every-screen injection DALT-8, and the empty no-profile placeholder CONTROL-2 are not yet built).

**Pending map:** `pendingACs` now holds exactly the **eight** still-pending ACs, each mapped to its owning behaviour phase (AC-2→DALT-6, AC-3→DALT-9, AC-4→DALT-10, AC-6→DALT-11, AC-7→DALT-5, AC-8→DALT-7, AC-9→DALT-8, AC-10→CONTROL-2). The scaffold guard that mirrors this (`unpended = {AC-1, AC-5}`, map length `10 - 2 = 8`) confirms the map shrank by exactly those two. The four augmentation rows (TestAC02→DALT-6, TestAC03→DALT-9, TestAC04→DALT-10, TestAC08→DALT-7) remain present and open in `modules/ITEST.md` §"Test augmentations" — each names the phase that un-pends its AC.

## Is the `referenceDaltonize` / `colorNear` grading fair?

**Fair, and the previously-disclosed coupling is now realized and confirmed.** `colorNear` (0.05 summed) is tight enough to reject the plausible wrong implementations — no-remap, wrong-type remap, and simulate-instead-of-distinguish — because the screen sample shifts far under each type (Lab Δ ≈ 16–71; sRGB shift ≈ 0.078 protan / 0.106 deutan / 0.510 tritan), while loose enough only to absorb the sRGB→CIELAB→sRGB round-trip rounding (measured 0 for the screen sample); a fixture guard confirms it separates the original from a real remap. With DALT-3 landed, the shipped `daltonize` does share the reference's error-redistribution design (full-strength `projectDichromat` view → lost a*/b* chroma rotated 90° → added back scaled by severity, lightness preserved), differing only in using the shipped `projectDichromat` where the reference uses the independent `referenceProjectDichromat`. The two agree to the 8-bit swatch for the screen sample, so the un-pended AC-1/AC-5 pass against an independent reference — the coupling G-2 flagged is now a confirmed design match, not an open risk.
