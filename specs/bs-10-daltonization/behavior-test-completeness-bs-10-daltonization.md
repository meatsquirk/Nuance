# bs-10 Daltonization — behaviour-test completeness

Independent adversarial grade of the bs-10 daltonization acceptance suite (re-graded 2026-10-14, **DALT-7** pass). I did **not** write these tests and changed no test or product file. Five behaviour phases have now landed and **un-pended** their ACs, so this is a re-grade against the previous (DALT-6) grid.

**What changed since the DALT-6 grid.** The build just completed **DALT-7 (AC-8: "Daltonization changes only what is shown, not stored values")**. DALT-7:

- changed **no `lib/` product code** — the remap `displayedSwatchColor`/`daltonizeColor` is a pure render-time transform called only by `ColorChip` (render) and the read endpoint; nothing writes it back to the stored `Sample`/`ColorCoordinates` or any store, so AC-8 holds structurally already;
- **un-pended AC-8** (removed its row from `bs10/pending.dart`; added `AC-8` to the scaffold guard's `unpended` set, so the pending map now holds exactly **five** ACs and the length check is `10 − 5 = 5`);
- **closed the TestAC08 augmentation row** by strengthening `TestAC08_StoredValuesUnchanged`: it now captures the Readout's numeric **stored-values** reading off (new harness getter `storedValuesText`, reading `SpaceSelector.valuesKey` — derived from `Sample.coordinates`, never the display remap); turns daltonization ON through the real shipped toggle; asserts the stored numeric reading is **unchanged** while on; adds the **control** that the displayed swatch *did* move away from the stored original to the remapped colour (`_remapOf(storedProfile)`, and that no swatch is still the original); then turns it OFF and asserts the swatch restores and the stored reading still holds;
- added one **chokepoint-grain unit test** to `test/display/color_simulation_test.dart` — "daltonization on remaps only the returned colour; a later off render still yields the original (no write-back, AC-8)" — the on render moves the colour (control), a following off render returns the original, and repeating the on render yields the same remap (a pure function of its arguments, carrying no state between calls).

In the DALT-6 grid AC-8 was **"B pending DALT-7"** precisely because its body never asserted the "on" swatch *did* change in between — the off→on→off restore could have been a no-op (the negative "unchanged" Then carried no in-test control). That control is now present and **discriminates against both the identity shell and the no-op** (the real deutan remap shifts ≈0.106 sRGB, outside `colorNear`'s 0.05, so the "swatch moved away / no swatch is still the original" control fails if the remap were the identity), and against a write-back impl (which would move the derived `storedValuesText`). **AC-8 therefore moves B → A** — justified under **G5** (the control now names and rejects the identity/no-op wrong implementation) and **G3** (the negative "stored unchanged" Then is now paired, after a `pumpAndSettle`, with a control at the AC's own shown-vs-stored grain proving the shown colour demonstrably changed). The stored-values equality stays tight under **G1/G4** and the control stays within AC-8 under **G6**. No other row changed grade band. New tally **8 A / 2 B-pending** (was 7 A / 3 B-pending).

The remaining **five** ACs are still **pending** (stage 3), graded on their design — what the code asserts — not on whether they currently skip. Two of them (AC-3/AC-4) are **green at the shell baseline by design**: turning daltonization on does not yet drive a screen-level behaviour their Then can separate from "off", so each carries a pre-seeded augmentation row owned by a later behaviour phase and is graded **"B pending <phase>"**, not A. The other three still-pending ACs (AC-6/AC-9/AC-10) fail at the red baseline on a real Then or precondition — they discriminate today — and are graded against grade-A design.

Surfaces read to verify every Then is tight and aimed at the right surface: `integration_test/daltonization_test.dart` (the AC tests + `_remapOf` / `_expectKnownSwatchRemapped`), `integration_test/daltonization_harness.dart` (the Given/When/Then vocabulary, fixtures, the independent `referenceDaltonize`, `displayColorOf`/`colorNear`/`displaySwatches`, and the new `storedValuesText` getter over `SpaceSelector.valuesKey`), `integration_test/bs10/pending.dart` (the pending gate), the spec `specs/bs-10-daltonization.feature`, and the catalogue + augmentations in `modules/ITEST.md` (§"Red baseline" / §"Test augmentations"). ## Did the DALT-7 control earn AC-8 its A (non-vacuous, discriminating, within-AC)?

**Yes.** The question is whether `TestAC08_StoredValuesUnchanged` would now reject the no-op / identity shell — the implementation the DALT-6 grid said it could not separate from a genuine render/store split (the off→on→off restore could have been a no-op).

- **Discriminates against the identity / no-op.** The control asserts that while daltonization is on, *no* rendered swatch is still `colorNear(screenSwatchColor)` **and** a swatch is `colorNear(_remapOf(storedProfile))` — a real deutan shift of ≈0.106 sRGB, outside `colorNear`'s 0.05 summed tolerance. Against an identity `daltonize`, the on swatch would still be the original, so both control assertions fail. The restore is therefore demonstrably a *genuine* round-trip over a colour that actually moved, not a no-op.
- **Discriminates against the write-back bug (the AC's own target).** `storedValuesText` is derived from `Sample.coordinates` through `readoutForSpace` (`SpaceSelector.valuesKey`), never from the display remap. An impl that wrote the transformed colour back to the sample/store would move that derived numeric reading, failing `h.storedValuesText == storedValuesOff`. So the negative Then is not vacuous: there is a plausible wrong impl under which the channel would change, and the test catches it.
- **Negative Then settled and paired (G3).** The "unchanged" reading is taken after `whenSetDaltonization`'s `pumpAndSettle`, and paired with a control at the AC's own **shown-vs-stored** grain: the shown swatch changed (and restored) while the stored reading held. This is the exact contrast the spec names ("changes only what is shown, not stored values"), so the pairing is at the right grain.
- **Within AC-8 (G6).** The primary claim remains "the stored colour values are unchanged"; the swatch-moved control is the contrasting "shown did change" half of the same claim, not AC-1's per-type remap assertion. One AC per test.

Grade **A**, a rule-justified move from the DALT-6 "B pending DALT-7".

## Is the AC-7 distinctness grading non-circular? Is the `referenceDaltonize` / `colorNear` grading fair?

Unchanged from the prior grids and re-confirmed. AC-7's rejection of "daltonize by simulating" leans on the **independent** `referenceProjectDichromat` at the acceptance grain and on the **separate shipped** simulation path (`simulateColor`/`projectDichromat`) at the DALT-5 unit grain — neither reuses `daltonize`'s own output as the expected value, so no circularity. `colorNear` (0.05 summed) is tight enough to reject no-remap, wrong-type and simulate-instead-of-distinguish (the screen sample shifts ≈0.078 protan / 0.106 deutan / 0.510 tritan) while absorbing only the sRGB round-trip rounding (measured 0 for the sample); a fixture guard confirms it separates the original from a real remap. With DALT-3 landed the shipped `daltonize` shares the reference's error-redistribution design and the two agree to the 8-bit swatch — the coupling G-2 ratified is a confirmed design match, not an open risk.
