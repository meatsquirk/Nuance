# bs-10 Daltonization — behaviour-test completeness

Independent adversarial grade of the bs-10 daltonization acceptance suite (re-graded 2026-10-14, **DALT-11** pass). I did **not** write these tests and changed no test or product file. Nine behaviour phases have now landed and **un-pended** their ACs, so this is a re-grade against the previous (DALT-10) grid.

**What changed since the DALT-10 grid.** The build just completed **DALT-11 (AC-6: "Changing the saved profile recomputes the remap")**. Like DALT-3/4/7/8/10 (and unlike the test-only DALT-9), DALT-11 ships a **real `lib/` change** — the reactive seam that lets a profile written straight to the store recompute the live remap:

- **`lib/store/persistent_store.dart`** — the `PersistentStore` interface now declares `Listenable get changes;` (a payload-free reactive seam). `InMemoryPersistentStore` is `with ChangeNotifier`, returns `changes => this`, and calls `notifyListeners()` from `put` and `delete`.
- **`lib/store/drift_persistent_store.dart`** — the same pattern (`with ChangeNotifier`, `changes => this`, notify on put/delete), so the shipped SQLite store carries the signal too.
- **`lib/store/cvd_profile_store.dart`** — new `Listenable get changes => _store.changes;` forwarding the backing store's signal (const constructor preserved).
- **`lib/app/build_app.dart`** — `_AppState.initState` constructs a `CvdProfileStore(widget.deps.store)` when a store is wired and listens to `changes`; `_handleStoreChanged` → `_reloadProfile` re-reads the saved profile and, when it differs from the live one, re-injects it through `AppScope` via the existing `withCvdProfile` live-profile seam; `dispose` removes the listener. A store write (the AC-6 harness path, which bypasses the bs-07 `LiveProfileScope.onProfileSaved` onboarding callback) now recomputes the live daltonization remap. The re-read is idempotent, so the production dual path (onboarding callback **and** store write) never double-applies.
- **`integration_test/bs10/pending.dart`** — AC-6 row removed; the map now holds **only** AC-10→CONTROL-2.
- **`integration_test/daltonization_test.dart`** — scaffold-guard `unpended` set now includes `AC-6` → `{AC-1, AC-5, AC-7, AC-2, AC-8, AC-9, AC-3, AC-4, AC-6}` (9), map length check `10 − 9 = 1`.

**One grade band changed: AC-6 A pending DALT-11 → A un-pended.** AC-6 was already grade-A on design; DALT-11 lands the behaviour it asserts, so `TestAC06_ProfileChangeRecomputes` now **runs on shipped behaviour** and is A for the same reasons — and it genuinely discriminates (see the dedicated section below). The grade band is unchanged (A→A); what moved is pending→un-pended. **The AC-6 (no augmentation row) reaches shipped-behaviour A.**

**No previously-A row regressed.** DALT-11's `lib/` change adds only a reactive notification + a root listener. The store listener is attached in `initState` **after** `givenDaltonization` has already written the setup profile (the save predates the listener), and it fires only on a store `put`/`delete`; no previously-A AC, smoke or guard writes the store mid-scenario (the daltonization toggle drives the `DisplayController`, not the store), so none triggers a spurious reload. `ColorChip` and the swatch render path are untouched, so `displaySwatches` is byte-for-byte unchanged and every swatch-reading AC (AC-1/2/3/5/8/9 + both swatch smoke tests) is unaffected; the provenance surfaces (AC-4) and the simulation/stored-value paths (AC-7/AC-8) are untouched. Trees with no store (`widget.deps.store == null`: bare unit trees, bs-01..09 harnesses) leave `_profileStore` null and attach no listener. **New tally: 10 A / 0 B.**

The remaining **one** AC is still **pending** (stage 3), graded on its design — what the code asserts — not on whether it currently skips. AC-10→CONTROL-2 fails at the red baseline on a real Then / precondition (the no-profile region is still an empty placeholder) — it discriminates today — and is graded against grade-A design.

Surfaces read to verify every Then is tight and aimed at the right surface: `integration_test/daltonization_test.dart` (the AC tests + `_remapOf` / `_expectKnownSwatchRemapped`), `integration_test/daltonization_harness.dart` (the Given/When/Then vocabulary, fixtures, the independent `referenceDaltonize`, `displayColorOf`/`colorNear`/`displaySwatches`, `storedValuesText`, `whenSaveProfile`/`whenClearProfile`, `remapColor`/`provenanceIcon`/`provenanceTintFor`, and the three `given…` screen assemblers), `integration_test/bs10/pending.dart` (the pending gate, now one AC), the spec `specs/bs-10-daltonization.feature`, and the module plans. ## Is AC-6's shipped-behaviour A earned (G5/G3)? Does the test discriminate?

**Yes.** The question is whether `TestAC06_ProfileChangeRecomputes` reads the *rendered* swatch (not a build-time value), would fail an impl that reads the profile once at build (pre-DALT-11), and has a tight before/after control.

- **It reads the rendered swatch.** Both the precondition and the Then call `_expectKnownSwatchRemapped`, which reads `displaySwatches(tester)` — the actual circular `BoxDecoration` swatch colours in the render tree.
