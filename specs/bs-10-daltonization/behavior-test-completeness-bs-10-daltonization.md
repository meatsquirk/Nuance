# bs-10 Daltonization — behaviour-test completeness

Independent adversarial grade of the bs-10 daltonization acceptance suite (re-graded 2026-10-14, **DALT-9** pass). I did **not** write these tests and changed no test or product file. Seven behaviour phases have now landed and **un-pended** their ACs, so this is a re-grade against the previous (DALT-8) grid.

**What changed since the DALT-8 grid.** The build just completed **DALT-9 (AC-3: "A remapped element still shows its label and value")**. DALT-9 is a **test-only** phase — it touched **no `lib/` body**. AC-3 is green at baseline because the product already satisfies it structurally: `lib/widgets/color_chip.dart` *asserts* a non-empty `label` and always renders `Flexible(child: Text(label))` beside the (optional) swatch, so a remapped colour can never be shown as a bare swatch; and the numeric lightness reading in `lib/readout/value_region.dart` (`_formatLightness(controller.lightness)` via `ValueReading`) is independent text derived from the stored `Sample.coordinates`, which the render-time remap never touches. DALT-9 therefore *strengthened the test* to prove the label + value survive a **real colour change**, rather than shipping new behaviour:

- **No PRODUCT change.** `lib/widgets/color_chip.dart`, `lib/readout/value_region.dart`/`value_reading.dart`, `lib/display/color_simulation.dart` (`displayedSwatchColor`) and `lib/a11y/cvd/daltonize.dart` are unchanged by this phase.
- **un-pended AC-3** (removed its row from `bs10/pending.dart`; added `AC-3` to the scaffold guard's `unpended` set in `daltonization_test.dart`, so the pending map now holds exactly **three** ACs — AC-4, AC-6, AC-10 — and the length check is `10 − 7 = 3`).
- **strengthened `TestAC03_LabelAndValueKept`.** It now reads the **OFF baseline** (`find.text('Displayed colour')` findsOneWidget, `find.text('55')` findsWidgets, and a swatch `colorNear(screenSwatchColor)` — the original), turns daltonization **ON** through the real panel toggle (`whenSetDaltonization(on:true)`), then asserts `_expectKnownSwatchRemapped` (a swatch is the `referenceDaltonize` remap **and** no swatch is still the original — the colour **changed**) **while** the same `'Displayed colour'` label and `'55'` reading are still present. The off→on comparison is the augmentation's control.
- **added unit test:** `test/widgets/color_chip_test.dart` — "with daltonization on, keeps its text label beside the remapped swatch (AC-3…)" locks the label-under-remap contract (swatch is the `daltonizeColor` remap, `isNot(original)`, while `find.text('Cool Teal')` findsOneWidget).

**One grade band changed: AC-3 B pending DALT-9 → A.** The strengthened `TestAC03` now discriminates. The off baseline pins the swatch as the original; turning daltonization on moves it onto the `referenceDaltonize` remap with **no swatch left at the original** (`_expectKnownSwatchRemapped`), while the label `'Displayed colour'` and the numeric `'55'` are still present. That proves the label + value **survive a genuine colour change**, not merely that they render under an identity remap. Against the ITEST red baseline (the DALT-2 identity shell, where "on" still showed the original) the `_expectKnownSwatchRemapped` step fails — so the augmentation discriminates, and the **TestAC03→DALT-9 augmentation row is now closed**. No previously-A row dropped (DALT-9 changed only test files, reused the shared `_expectKnownSwatchRemapped` unchanged, and the scaffold guard's `unpended`/length check stays consistent). **New tally: 9 A / 1 B-pending (AC-4 → DALT-10).**

## Is AC-3's move to A earned (G5/G3), and is the augmentation discriminating?

**Yes.** The question is whether the strengthened `TestAC03` proves the label + numeric value **survive a real colour change**, rather than merely rendering under an identity remap — and whether the augmentation would fail against the DALT-2 identity-shell baseline.

- **The off baseline establishes the starting point.** Before the When, the test asserts the label `'Displayed colour'` (findsOneWidget), the numeric `'55'` (findsWidgets), and a swatch `colorNear(screenSwatchColor)` — the known swatch is the **original** colour while off.
- **The When drives a real colour change.** Turning daltonization on through the real panel toggle routes the swatch through the shipped `daltonizeColor` (DALT-3), which actually moves the colour (deutan shift ≈0.106 sRGB > the 0.05 `colorNear` tolerance).
- **The Then proves survival across that change (G3/G5).** `_expectKnownSwatchRemapped` asserts a swatch is the `referenceDaltonize` remap **and** no swatch is still the original — i.e. the colour demonstrably **changed** (this is the control: the swatch is the reading that CAN change, and here did) — **while** the same `'Displayed colour'` label and `'55'` reading are still present. The label + value assertions are therefore made under a proven real remap, not an identity no-op.
