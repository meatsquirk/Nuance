# bs-10 Daltonization — behaviour-test completeness

Independent adversarial grade of the bs-10 daltonization acceptance suite (re-graded 2026-10-13, **DALT-6** pass). I did **not** write these tests and changed no test or product file. Four behaviour phases have now landed and **un-pended** their ACs, so this is a re-grade against the previous (DALT-5) grid.

**What changed since the DALT-5 grid.** The build just completed **DALT-6 (AC-2: "with daltonization off, colours are shown unremapped")**. DALT-6:

- made the chokepoint's **off path explicit and verified** — `displayedSwatchColor` routes `settings.daltonization ? daltonizeColor : simulateColor`, so with daltonization off the colour never touches `daltonize` (and never consults the stored profile); off = `simulateColor`, which with no simulation set is the stored original;
- **un-pended AC-2** (removed its row from `bs10/pending.dart`; added `AC-2` to the scaffold guard's `unpended` set, so the pending map now holds exactly **six** ACs and the length check is `10 − 4 = 6`);
- **closed the TestAC02 augmentation row** by adding the planned **on-remaps-away control** to `TestAC02_OffShowsOriginal`: after asserting the off state it opens the shipped panel, toggles daltonization ON, and asserts the swatch moves away from the original (`displayedColor == _remapOf(storedProfile)`, `≠ original`, and `_expectKnownSwatchRemapped`);
- added one **chokepoint-grain unit test** to `test/display/color_simulation_test.dart` — "daltonization off → the original regardless of the stored profile (AC-2)" — pinning that the off branch does not leak a remap or read the profile, with an on-control showing the same strong profile *does* move the colour.

In the DALT-5 grid AC-2 was **"B pending DALT-6"** precisely because it carried no on-control and so could not show "off" differs from a real remap. That augmentation is now present and **discriminates against the pre-DALT-3 identity shell** (the real deutan remap shifts ≈0.106 sRGB, outside `colorNear`'s 0.05, so every control assertion fails if the remap were the identity). **AC-2 therefore moves B → A** — justified under **G5** (the in-test control now names and rejects the identity-shell wrong implementation) with the off direction still tight under **G1/G4** and the control staying within AC-2 under **G6**. No other row changed grade band. New tally **7 A / 3 B-pending** (was 6 A / 4 B-pending).

The remaining **six** ACs are still **pending** (stage 3), graded on their design — what the code asserts — not on whether they currently skip. Three of them (AC-3/4/8) are **green at the shell baseline by design**: turning daltonization on does not yet drive a screen-level behaviour their Then can separate from "off", so each carries a pre-seeded augmentation row owned by a later behaviour phase and is graded **"B pending <phase>"**, not A. The other three still-pending ACs (AC-6/9/10) fail at the red baseline on a real Then or precondition — they discriminate today — and are graded against grade-A design.

## Did the DALT-6 on-control earn AC-2 its A (non-vacuous, discriminating, within-AC)?

**Yes.** The question is whether `TestAC02_OffShowsOriginal` would now reject the pre-DALT-3 identity shell — the implementation the DALT-5 grid said it could not separate from a real off-state.

- **Discriminates against the identity shell.** The control computes `remapped = _remapOf(storedProfile) = displayColorOf(referenceDaltonize(SCREEN_SAMPLE_LAB, deutan@0.6))`, a real shift of ≈0.106 sRGB (deutan), comfortably outside `colorNear`'s 0.05 summed tolerance. Against an identity `daltonize`, `displayedColor` with daltonization on would still return the original, so `expect(colorNear(displayed, remapped), isTrue)`, `expect(colorNear(displayed, original), isFalse)` and `_expectKnownSwatchRemapped` would each fail. The control is therefore a genuine foil, not a tautology.
- **Off direction still tight (G1/G4).** Both the rendered swatch (`displaySwatches` → `colorNear(screenSwatchColor)`) and the pipeline (`h.displayedColor(original) == original`) are asserted off, after the off Given is checked through the live endpoint (`daltonization`/`settings.daltonization`).
- **Behaviour answers (G2/G3).** The on-control toggles through the shipped panel (`whenOpenSettings`/`whenSetDaltonization(on:true)`/`whenCloseSettings`), each `pumpAndSettle`'d, and the resulting on-state is read through the same live endpoint — the setting answers, and the reading is shown to change.
- **Within AC-2 (G6).** The primary assertion remains "off shows the unremapped original"; the on-reading is the contrasting half of the same off-vs-on pair for the same sample (the pairing G3 asks for), not AC-1's per-type claim. One AC per test.

Grade **A**, a rule-justified move from the DALT-5 "B pending DALT-6".

## Is the AC-7 distinctness grading non-circular? Is the `referenceDaltonize` / `colorNear` grading fair?

Unchanged from the DALT-5 grid and re-confirmed. AC-7's rejection of "daltonize by simulating" leans on the **independent** `referenceProjectDichromat` at the acceptance grain and on the **separate shipped** simulation path (`simulateColor`/`projectDichromat`) at the DALT-5 unit grain — neither reuses `daltonize`'s own output as the expected value, so no circularity. `colorNear` (0.05 summed) is tight enough to reject no-remap, wrong-type and simulate-instead-of-distinguish (the screen sample shifts ≈0.078 protan / 0.106 deutan / 0.510 tritan) while absorbing only the sRGB round-trip rounding (measured 0 for the sample); a fixture guard confirms it separates the original from a real remap. With DALT-3 landed the shipped `daltonize` shares the reference's error-redistribution design and the two agree to the 8-bit swatch — the coupling G-2 ratified is a confirmed design match, not an open risk.
