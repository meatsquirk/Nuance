# bs-10 Daltonization — behaviour-test completeness

Independent adversarial grade of the bs-10 daltonization acceptance suite (re-graded 2026-10-14, **DALT-8** pass). I did **not** write these tests and changed no test or product file. Six behaviour phases have now landed and **un-pended** their ACs, so this is a re-grade against the previous (DALT-7) grid.

**What changed since the DALT-7 grid.** The build just completed **DALT-8 (AC-9: "Daltonization applies on every screen while it is on")**. DALT-8 is the first behaviour phase since the DALT-3 keystone to touch `lib/` bodies — every screen now surfaces a colour swatch through the **one** shared `ColorChip`/`DisplayScope` chokepoint, so the remap reaches capture, readout and palette rather than the Readout alone:

- **PRODUCT change.**
  - `lib/capture/capture_current_reading.dart` (**new**): renders the Capture screen's live `currentSample` colour through `ColorChip` (reading the enclosing `AppScope.colorScience`), labelled with the reading's CIELAB value so the swatch never stands alone (SI §5.1); it is wired into `lib/capture/capture_screen.dart` above the bs-09 readings region. It renders nothing before a sample exists or with no `AppScope` (standalone unit context) — the pre-bs-10 capture layout is otherwise unchanged.
  - `lib/palette/paint_row.dart` + `lib/palette/paint_list_region.dart`: each "My paints" `PaintRow` now renders its masstone through a `ColorChip` swatch (colour from `AppScope.colorScience`, `null` outside a scope → plain-text name as before). The new `PaintRow.swatchKeyFor(id)` anchors the chip; the name becomes the chip's label, so the swatch is never shown alone.
  - All three surfaces route through the existing `displayedSwatchColor` chokepoint (`settings.daltonization ? daltonizeColor : simulateColor`), so daltonization remaps on every screen with no new transform code and no write-back (AC-8 preserved: the masstone/coordinates are unchanged; the remap is render-time only).
- **un-pended AC-9** (removed its row from `bs10/pending.dart`; added `AC-9` to the scaffold guard's `unpended` set in `daltonization_test.dart`, so the pending map now holds exactly **four** ACs — AC-3, AC-4, AC-6, AC-10 — and the length check is `10 − 6 = 4`).
- **HARNESS FIXTURE FIX.** `daltonization_harness.dart`'s `screenPalette` was renamed from `'Screen palette'` to `PaletteController.myPaintsName` ("My paints"). `PaletteController.myPaints` (what `PaintListRegion` renders) returns paints only for the palette **named exactly "My paints"**; a palette under any other name yields an empty `myPaints`, so `PaintListRegion` would render "No paints yet" and no `PaintRow` — the AC-9 Given ("the known swatch is surfaced on the Palette screen") would not hold, and `_expectKnownSwatchRemapped` would fail on `isNotEmpty`. The rename makes the Given faithful to the production filter; the AC-9 Then (swatch remapped on each screen) is **unchanged**. Judged legitimate below (§"Is the DALT-8 fixture rename legitimate…").
- **added unit tests:** `test/capture/capture_current_reading_test.dart` (new), `test/palette/paint_list_region_test.dart` (new), and a `swatchColor` case in `test/widgets/paint_row_test.dart`.

**No grade band changed.** AC-9's test `TestAC09_EveryScreen` was already graded **A** in prior grids (its design was sound at ITEST-2; it was red at the baseline and is now green on shipped behaviour across the three screens). It was counted under the A band in the DALT-7 grid while still pending; it stays **A** and now runs on shipped behaviour. The two remaining B-pending ACs are unchanged: **AC-3 (→DALT-9)** and **AC-4 (→DALT-10)**. Tally stays **8 A / 2 B-pending**.

The remaining **four** ACs are still **pending** (stage 3), graded on their design — what the code asserts — not on whether they currently skip. Two of them (AC-3/AC-4) are **green at the shell baseline by design**: turning daltonization on does not yet drive a screen-level behaviour their Then can separate from "off", so each carries a pre-seeded augmentation row owned by a later behaviour phase and is graded **"B pending <phase>"**, not A. ## Is the DALT-8 fixture rename legitimate (not a weakening), and does AC-9 earn its A on shipped behaviour?

**The rename is legitimate.** `PaletteController.myPaints` returns paints **only** for the palette whose name is exactly `myPaintsName` ("My paints"), and `PaintListRegion` renders `controller.myPaints`. Before DALT-8 the fixture `screenPalette` was named `'Screen palette'`, so `myPaints` would have been empty, `PaintListRegion` would have shown "No paints yet", and no `PaintRow` (hence no swatch) would exist on the palette screen. In other words the AC-9 Given — "the known swatch is surfaced on the Palette screen" — **would not actually hold**, and `_expectKnownSwatchRemapped` would have failed on its `isNotEmpty` guard rather than on the remap assertion. Renaming the fixture to "My paints" makes the Given *faithful to the production path* (the My-paints view shows only the "My paints" palette); it does not touch the Then, does not relax `_expectKnownSwatchRemapped`, and does not make the test pass where the behaviour is absent — a palette with no remap would still fail the "a swatch matches the reference AND none is still the original" assertion. This is a correct Given fix, not a loosened assertion.

**AC-9 earns its A on shipped behaviour.** The test now runs un-pended and exercises the real chokepoint on all three screens:

- **It tests the production chokepoint, not a per-screen re-implementation.** Readout, Capture (`CaptureCurrentReading`) and Palette (`PaintRow`/`PaintListRegion`) all feed their colour into the single `ColorChip` → `displayedSwatchColor` seam. AC-9 asserts the remap reaches every screen, which is exactly the "one cross-cutting service injected into every screen" claim (SI Accessibility) — and it is now observable because each screen surfaces a swatch through that one seam.
- **It discriminates (G5).** A remap wired into one screen only, or a screen that surfaces no swatch, fails its `_expectKnownSwatchRemapped` (empty swatches, or a swatch still at the original). The assertion remains per-screen and at value against the independent `referenceDaltonize`, so a type-blind or identity remap also fails. It was genuinely red at the DALT-7 baseline (capture/palette had no swatch to remap) and is green only because DALT-8 shipped the swatches through the chokepoint.
