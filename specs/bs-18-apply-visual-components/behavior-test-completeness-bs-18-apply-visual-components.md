## Transparency notes (do not drop any row below its stated grade)

1. **AC-2 omits the scenario's "back/close affordance" clause — acceptable scoping, not a plain B.** The scenario Then has three clauses (Atkinson title; "the back or close affordance that destination needs"; theme toggle); the test asserts the first and third and omits the second. Verdict: **acceptable scoping.** (a) All five surfaces in AC-2's roster are top-level nav destinations, which *need no* back/close — so the conditional clause "the affordance that destination needs" is satisfied vacuously, and asserting a *present* leading affordance would be wrong for these roots. (b) `AppTopBar` renders its `leadingKey` only when `onBack`/`onClose` is non-null, and the harness pumps every deep-link screen **as a root** (`pumpScreen` boots a fresh app rooted at that screen), so no back can be reliably asserted on this roster. (c) Neither of AC-2's **catalogue Rejects** ("ad-hoc header without the toggle"; "hardcoded title style") concerns the affordance — both are fully caught. The screens that genuinely need a back/close (Display settings, onboarding) are the CFG screens graded under **AC-10 (ITEST-3)**, not AC-2. If the author wishes to belt-and-suspender it, a cheap addition is `expect(find.byKey(AppTopBar.leadingKey), findsNothing)` on each root surface (asserting the *absence* the roots need) — but this is a strengthening, not a correctness gap, so AC-2 grades **straight A**. Marked ◑ on G4 for the omission; not gate-blocking.
2. **AC-1 is green at baseline but fully discriminates at design time.** CHROME-2 already shipped the conformant nav (4 destinations, filled-vs-outline active marker, theme-token fill/hairline), so all AC-1 assertions pass at the red-baseline run. The grade is of the test **design**: it rejects both catalogue Rejects ("a destination missing" via `hasLength(4)` + per-destination finders; "active by colour only" via the filled/outline glyph + non-colour marker key) and a hardcoded-colour impl via the two token equalities. CHROME-3 (AC-1's owner) un-pends it and keeps it green; no augmentation is pre-seeded or owed for AC-1.
3. **AC-3 and AC-5 are A-core by the pre-seeded augmentation table, not plain B.** Both author the *present-side* of the swap and catch their catalogue's **named** Rejects (AC-3: torch/import/shutter ad-hoc; AC-5: bare-Column region / IconButton speak). What each defers is the *exhaustive "superseded ad-hoc widget absent"* sweep — AC-3 over **every** capture control (not just torch/import), AC-5 over a region/speak that carries BOTH the new wrapper and a leftover old `Card`/`IconButton`. Both screens are **partly swapped today**, which is exactly why `modules/ITEST.md` pre-seeds TestAC03→READ-1 and TestAC05→READ-3: the absent-sweep is the swapping phase's to add as it un-pends. These are later-only limits the ITEST-2 authoring phase cannot close (the controls are not yet swapped), so each is "A-core / B pending `<owner>`", which PASSES the gate — not a plain B.
4. **AC-4 chose the three always-present banners deliberately.** The scenario speaks of stability/accuracy/warning readings; the test anchors on `{stabilityKey, lockIndicatorKey, accuracyKey}` — the three `Positioned` readings `CaptureLiveView` always renders (the low-light and torch warnings sit behind `Visibility` and need not be live under `aReading`). This makes the `present.length >= 2` Given genuinely true and keeps the pairwise-rect check non-vacuous; faithful to the AC's grain.
