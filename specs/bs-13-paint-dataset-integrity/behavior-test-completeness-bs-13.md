## AC-3 allow-list judgment (project_source as a ratio authority)

GUARD-2's `kRatioProducerAuthorities` allow-lists **two** `lib/` files that may construct a `RecipeComponent.partsFraction`:

- `lib/recipes/engine/subtractive_engine.dart` — the physics solver, which **originates** every ratio (`partsFraction: share` at line 386). This is the spec's "the ratios come from the physics solver".
- `lib/projects/project_source.dart` — which **rehydrates** a persisted recipe (`_componentFromJson` at line 154, `partsFraction: (json['partsFraction'] as num).toDouble()`). The persisted ratio it reloads was produced by the solver earlier (bs-04) and saved by the painter (bs-06); it is round-tripped through the on-device store, never read from the seed or any LLM source. The write side (`_recipeToJson`) only serialises a `Recipe.component.partsFraction` that the solver produced.

**Judgment: the allow-list is spec-faithful and does NOT weaken the guard.** AC-3 forbids a ratio *originating from the LLM/seed*; `project_source` only reconstitutes a previously-solver-produced ratio, so no LLM/seed ratio can reach a shipped recipe through it. A grep confirms these two files are the *only* `partsFraction:` production sites in `lib/` (every other `partsFraction` occurrence is a member read `c.partsFraction`, a field declaration, or a masked string key such as `'partsFraction':`), so the shipped empty result genuinely rests on exactly these two sanctioned origins.

Two minor, non-downgrading observations (neither owed to any phase, since GUARD-2 is last):
1. The source-scan facet exempts `project_source.dart` **whole-file**, not just line 154. In this small persistence file the only `partsFraction:` construction is the legitimate rehydration, so there is no practical hole; a future ratio-producing site added to that file would, however, be silently exempt.
2. The AC-3 **control** (`roots: control_llmRatio, schemaFiles: control_llmRatio`) actually fires through the **schema facet** (facet 2 matches the control's `partsFraction` field declaration), not the source-scan facet (facet 1 needs a `partsFraction:` colon-production, which the control fixture — `final double partsFraction;` / `this.partsFraction` — does not contain). The control therefore proves the schema facet discriminates but does not independently exercise the source-scan allow-list's upper bound (a too-*broad* allow-list would not be caught; a too-*narrow* one is, via the shipped `isEmpty` over the real solver sites). G5 is still satisfied — the test carries a discriminating control and catches multiple plausible wrong impls — so this does not drop AC-3 below A; it is recorded for transparency.
